# 需求雷达 PRD 与会话交接

版本：v0.1｜日期：2026-09-15｜状态：需求与实施建议，尚未开发

## 1. 结论与本次目标

先做需求雷达，用它研究「电商图片处理中的付费需求」，再结合行业用户反馈确定生图产品定位。雷达从第一版就面向未来收费，小分队是首批限额试用用户。

本文是下一会话的主要上下文。已确认方向继续执行；功能细节、验收数量和技术方案是建议基线，可依据数据试验调整，不代表已完成或已验证。

## 2. 需求背景与已确认上下文

用户正在做 AI 出海实践，有两个项目：生图产品、需求发现雷达。当前学习网站已有 AI 出海路线图、教程和生图实践记录，但缺少具体项目计划与执行记录。

### 已确认

- 生图底座已具备：用户有基于 ChatGPT 模型的生图 API，支持根据参考图进一步编辑。具体接口、费用、耗时、稳定性和使用条件尚未核对。
- 生图产品尚未确定目标用户、场景和优势，需要通过搜索、竞品分析和用户验证确定。
- 生图不以小分队的内容创作者、独立开发者为目标客户。用户认为这些成员的一般生图任务可用豆包或 ChatGPT 网页版完成。
- 优先深挖其他行业，首个研究专题选电商图片工作流；尚未选定商品品类、市场、最终功能或付费客户。
- 小分队有内容创作者、独立开发者，暂时没有已知电商卖家。这些成员可以试用雷达、研究各自项目，不能替代电商客户验证。
- 雷达前期供大家一起用，后续明确采取收费模式。
- 用户有服务器，尚无收款账户；每日可投入时间、预算、服务器环境未明确。
- 用户希望两周内交付两个 MVP。顺序调整为雷达先行，获得研究结果后推进生图，不能等待完整雷达才开始研究。
- 用户最关注数据获取：如何通过搜索或采集获得真实需求；分析模型强，不代表源数据真实、完整或能证明付费意愿。
- 本轮只要求把 PRD 和关键上下文落到仓库，供晚上新会话继续。没有要求现在开发、部署或接入付费服务。

### 不要恢复的旧假设

- 不按原先四周计划推进。
- 不因容易接触，就把小分队成员定为生图客户。
- 不把商品换背景、饰品保真、封面生成等讨论例子写成最终定位。
- 不把雷达做成仅靠手动录入的笔记工具；主动发现真实线索是核心。
- 不把搜索结果、AI 分数、朋友鼓励当成需求或付费验证成功。

## 3. 解决的问题与产品定位

### 当前问题

1. 有开发与模型能力，却不知道哪些人存在值得解决的问题。
2. 手动搜索分散、耗时，结果中广告、榜单、推广和重复内容多。
3. 线索缺上下文和原始来源，难区分真实经历、个人推测和 AI 补写。
4. 收集完不知道先验证哪个，后续试用结果没有回填，容易反复研究。

### 产品定位

帮助独立开发者和 AI 出海创业者，结合自身能力，从公开讨论中发现有出处、值得进一步验证的需求，并跟进验证结果。

用户购买的价值假设：减少无效搜集和筛选时间，持续获得与自己有关的需求证据。是否值得收费，仍需用真实使用和付费试验确认。

### 首个研究任务

输入：已有参考图编辑 API 和网站开发能力；两周内做小产品；研究电商图片任务。

期望输出：三个有证据的候选问题，分别写清人群、工作场景、当前办法、代价、竞品、未解决问题和下一步验证动作。

示例（假设，非研究成果）：卖家批量上新时需要逐张修正标签、修改尺寸；值得验证的是整套处理与返工成本，不能直接推断需要另一个生成按钮。

## 5. MVP 范围

### 阶段 A：先证明能获取有用数据（第 1—2 天）

- 输入研究方向和条件，生成可检查的搜索词。
- 至少验证两类来源的发现、获取与证据保存链路。
- 运行真实搜索，读取可获取的原文；保存实际失败情况。
- 输出候选线索与需求卡，可通过简单页面或结构化研究产物验收。
- 记录相关性、可追溯性、重复率、推广比例和成本。

### 阶段 B：供多人使用的 MVP（两周内）

| 编号 | 功能 | 需求与验收要点 |
| --- | --- | --- |
| R01 | 研究项目 | 新建、编辑研究方向、能力、用户范围、时间约束、排除条件；未填的信息保持未知 |
| R02 | 主动扫描 | 手动触发真实搜索；展示进度、时间范围、来源与失败；不能以预置数据冒充结果 |
| R03 | 证据提取 | 原文片段、链接、日期、上下文、获取状态可查看；译文与原文分开 |
| R04 | 需求归类 | 合并相似问题，保留全部证据关联；用户可纠正误归类和推广标记 |
| R05 | 机会判断 | 展示人群、任务、现有办法、已知代价、适配理由、反例、未知项和验证建议 |
| R06 | 保存与筛选 | 按项目、来源、时间、证据状态和验证状态筛选；保存到服务器，刷新或换设备可恢复 |
| R07 | 验证跟进 | 记录交流、试用、采用、付款或否定结果；备注实际行为与证据，可修改并保留更新时间 |
| R08 | 账户与额度 | 邀请试用、个人项目隔离、扫描限额、用量记录；成员不能读取别人的私有项目 |
| R09 | 导出 | 导出 Markdown 研究报告，包含来源、未知项、决策和下一步，方便继续开发 |

多人共用指多个独立账户可使用产品，默认研究数据私有。共享研究空间、团队角色和共同编辑后置，避免把小分队共用误做成所有资料公开。

### 本轮不做

- 全网全量抓取、所有平台接入、实时监听、复杂定时任务。
- 自动私信、自动发帖、代替用户联系潜在客户。
- 绕过登录、验证码、付费墙或平台限制获取数据。
- 用 AI 预测收入或宣称需求已经得到市场验证。
- 完整团队协作、移动 App、复杂订阅与发票系统。
- 在雷达内嵌生图编辑器；两个产品可以互相供给信息，但保持用途清晰。

## 6. 数据获取设计：首要验证项

### 6.1 搜索策略

以「人群 × 任务 × 问题 × 现有办法」组合查询，不只搜索“AI 生图需求”。

- 人群：电商卖家、某类商品经营者、图片运营人员等。
- 任务：上新、批量修图、场景图、广告素材、尺寸适配。
- 问题：耗时、反复修改、颜色变化、标签错误、不一致。
- 替代办法：现有编辑工具、AI 商品图工具、摄影和设计外包。

例如：`"product photos" "labels" "changing"`。查询只是探索入口，结果不足时根据用户原话调整，不机械扩充关键词数量。

### 6.2 候选来源与获取方式

| 来源类型 | 主要寻找 | 获取试验 | 注意事项 |
| --- | --- | --- | --- |
| 行业社区公开讨论 | 求助、最近一次经历、替代方案 | 搜索发现链接，再通过可用接口或允许的页面读取获得上下文 | 区分用户经历和工具推广 |
| 工具评价、支持论坛 | 用后不满、功能缺口、反复出现的问题 | 先选可稳定获取的少量站点 | 评价有选择偏差，不代表整个用户群 |
| 公开外包需求 | 工作量、交付要求、公开预算 | 核对公开可访问性与使用条件后试取 | 发布预算不等于成交价；不获取私有资料 |

搜索服务和采集供应商尚未选定。实施时核对覆盖、原文获取、商业使用条件、费用、限额与保存/删除要求。一个搜索供应商返回多个站点，不等于验证了多种独立获取方式；报告应分别记录供应商、来源类型和站点。

首版：一个主搜索接口，配少量来源读取方式及手动补录入口。手动补录用于补充证据，不能替代主动搜索。不得把所有数据依赖在一个未经验证的平台接口上。

### 6.3 处理链路

输入 → 查询生成 → 搜索发现 → 原文获取 → 去重与噪声标记 → 证据提取 → 问题归类 → 机会卡 → 人工验证 → 结果回填。

- 搜索摘要只作为摘要保存；未取得原文时标为 `snippet_only`，不编造引语或上下文。
- 发布日期无法确认时留空；抓取日期不能替代发布日期。
- 去重优先规范化链接，再比对内容；转发、复制文章不增加独立证据数。
- 保留事实、译文和模型推测的边界；每个事实性结论应能找到支撑证据。
- 同时保留否定证据，例如用户已经满意地使用竞品，而非只搜支持观点。
- 网页内容属于不可信输入，不执行其中指令、脚本或索取密钥的要求。
- 页面读取拒绝内网、本机及非 HTTP(S) 目标，并检查重定向，避免链接抓取访问服务器内部资源。

### 6.4 失败与成本规则

- 任务状态建议：`queued / running / partial / succeeded / failed / cancelled`。
- 展示各阶段失败原因；部分来源失败可返回已有结果，并明确覆盖不足。
- 429/临时故障采用有限重试；拒绝访问时记录原因，不反复绕过限制。
- 每轮有请求数、运行时间和费用上限；额度不足时不启动新任务。
- 重复点击不重复启动同一请求；用量与供应商费用分开记录。
- 若采取预占额度，失败/取消释放未使用额度；部分成功结算规则实施前明确展示，不能重复扣减。
- 页面关闭不丢失服务器任务状态；刷新后可查看进度和已有结果。

## 7. 证据与机会卡

### 建议的最小数据结构（尚非已实现数据库或 API）

| 对象 | 主要字段 |
| --- | --- |
| ResearchProject | id、ownerId、title、capabilities、audienceScope、market、language、constraints、exclusions、createdAt |
| Scan | id、projectId、querySnapshot、sourceConfig、timeRange、status、startedAt、finishedAt、errorSummary、usage、cost、costCurrency |
| Evidence | id、scanId、url、canonicalUrl、sourceType、publishedAt（可空）、fetchedAt、excerpt、context、translation、fetchStatus、promotionFlag、duplicateGroupId |
| Opportunity | id、projectId、audience、task、problem、currentWorkaround、observedCost、evidenceIds、counterEvidenceIds、fitReason、unknowns、nextExperiment、status |
| ValidationRecord | id、opportunityId、actionType、outcome、note、evidenceLinks、occurredAt、createdBy |
| UsageRecord | id、accountId、scanId、provider、operation、units、estimatedCost、actualCost（可空）、currency、idempotencyKey |

不要求保存个人身份信息；能够依来源链接判断独立性时，不额外采集用户资料。原文保存范围和保留周期应符合对应来源要求，首版优先必要片段和链接。

### 判断规则

- 证据获取状态：`full_context / snippet_only / unavailable`，描述材料完整程度。
- 机会跟进状态：`new / saved / investigating / experimenting / paused / rejected`，描述处理进度。
- 实际结果另记：已交流、提交素材、采用、再次使用、真实付费；“已试用”不能自动升级为“已付费”。
- 优先展示独立证据、实际代价、可接触性、能力匹配和未知项。总分不是首版必要功能。
- 若增加评分，每项必须说明依据；证据缺失标未知，不用模型猜测填满分数。
- 样本中的出现频率不等于市场频率；公开预算、询价、支付意向和实际成交分开。

## 8. 页面与交互建议

1. **项目列表**：已有研究、最近扫描、剩余额度；新用户可选择“电商图片工作流”作为起始专题。
2. **研究设置**：填写条件、查看并调整搜索范围，显示扫描额度消耗和边界。
3. **扫描结果**：进度、来源覆盖、问题列表、筛选；空结果解释实际情况并建议缩小或改变查询。
4. **机会详情**：问题、证据原文、现有办法、未知项、保存/排除和下一步验证。
5. **验证记录**：行动与结果时间线，支持导出含证据的研究报告。

原文打不开时显示失效，不删除既有结论的历史依据，也不继续声称来源当前可访问。删除项目应有明确确认，删除范围、历史费用记录处理方式在实施时确定。

## 9. 验收与判断是否值得继续

### 数据关口：第 1—2 天的暂定目标

- 验证至少两类来源，记录实际站点、获取方式及失败。
- 收集约 30 条候选材料，按预先固定的抽样方式人工核对 20 条，不能只挑最好结果。
- 暂定通过线：20 条中至少 12 条与具体图片任务相关，至少 10 条有可核对原文和上下文；产出三个候选问题，每个关联至少两条独立原文证据。
- 上述数字是工程起步门槛，不代表统计显著或商业需求成立。未达到时优先调整查询、来源与噪声过滤。
- 记录相关条数/抽样数、原文可核对条数/抽样数、重复条数/候选数、推广条数/抽样数，以及总成本和运行时间。

### 两周雷达 MVP 验收

- 新用户能建立自己的研究项目，真实扫描并查看可追溯的证据。
- 能保存、排除、跟进、导出；刷新和更换设备后数据仍在。
- 两个账户互相无法访问私有项目、任务和报告；检查服务端权限，而非只隐藏按钮。
- 能处理空结果、只得到摘要、来源失效、超时、限流、重复提交和额度不足。
- 每轮搜索及模型用量可追踪，有费用上限；日志中不出现密钥。
- 邀请小分队成员研究各自问题，记录哪些结果被保存、进入真实验证，以及是否回来再次扫描。

### 与生图定位的交接产物

一份定位报告：候选人群与场景、独立证据、竞品及替代办法、未解决问题、可交付优势假设、接触用户的渠道、样例实验、继续/调整决定。

报告不能直接承诺生图保真、降低成本或付费转化。需要用用户 API、代表素材和真实目标用户验证。

D4 是决策关口。没有可靠证据时，不假装定位已确认：明确缺口，缩小实验范围，并说明两周双 MVP 的影响。用户能投入的时间、接口获取和外部用户响应仍会影响工期。

## 11. 商业化与外部依赖

- 小分队先限额试用，不承诺永久免费或无限扫描。
- 付费价值假设：更多研究项目/扫描额度、持续追踪；团队协作后置。
- 暂不定价格，先测搜索、页面获取、分析与存储成本，再验证用户付费意愿。
- 用户尚无收款账户。首版做用量和额度，真实支付接入需后续确认服务条件与账户，不展示虚假支付成功。
- 需要补充：搜索供应商和预算上限、可用文本分析模型、服务器环境与部署方式、每天可投入时间。
- 生图 API 费用和性能用于后续定位可行性判断；雷达本身还需要文本分析能力，不能假设生图接口支持。
- 不把密钥写入 PRD、公开仓库或前端；实施时使用服务器环境变量等合适方式配置。
