# 需求雷达：数据来源可行性试验

日期：2026-09-15｜状态：研究链路部分可行；生产接入与付费需求未验证。

会话后续更新：用户已确认有文本大模型 API，稍后提供资料。下一轮由服务器调用模型自动提取和归类，见[最新交接](../../../demand-radar-handoff.md)。本次手动研究只是来源试验，不是产品运行方式。

## 结论

继续雷达先行，不改 PRD 方向。已跑真实搜索，登记 30 条候选、固定核对前 20 条，并验证少量普通 HTTP 页面读取。**可以开发单人扫描到研究报告的最短链路；尚不能宣称收费雷达的数据接入已就绪。**

电商图片优先，短剧未采样。小分队仍是雷达试用用户。生图定位不因这次搜索直接确定。

- 证据较具体：批量图片匹配、上传和改名。它们主要是流程问题，未必需要生图 API。
- 生图相关：场景图中的标签、颜色和材质保真。但存在竞品已满足需求的反例。
- 付费：只看到公开标价线索，没有核实付款、成交价或软件购买意愿。
- 两周计划：先完成生产搜索账户与数据权限核对，再估算多人 MVP 工期；不能把本会话网页工具当作已接入的后端服务。

相关：有明确电商图片处理、组织或发布任务；教程、推广也可相关，但不得当买家证据。泛泛的没销量、行业竞争、混合职位分类页判不相关。前 20 条中的摘要也按可见内容判断，原文状态另算。

## 7. 可开发的最短链路

先做一个服务器命令/任务入口和结构化报告，不做页面：

```text
研究条件 → 固定查询清单 → 主搜索接口
        → URL 去重 → 已核对权限的页面读取
        → 保存必要片段/日期/获取失败
        → 文本模型提取 → 程序校验与模型归类 → Markdown 报告
```

1. **搜索适配器**：优先试 Tavily basic。独立保存 query、rank、原始 URL、搜索摘要与取数时间；用户可检查搜索词。拿到 key 后在服务器重跑，不拿本轮数据充当新扫描。
2. **读取适配器**：先评估 Shopify 社区和应用评价；只有确认允许的来源进入自动读取名单。其余保留链接和合法可保留的摘要，标 snippet_only。授权未解决时此步骤仍是生产阻塞项。
3. **最小存储**：单人试验用 JSONL/文件；真正服务器任务建议复用现有可用数据库，服务器环境未知所以不预定框架。保存 Scan、Evidence、Usage，不把 localStorage 当多人存储。
4. **结果处理**：规范 URL、帖子 ID 去重；同文转载关联 duplicateGroupId。先规则过滤分类页、招聘无关类别、发布推广，再由文本模型自动提取与归类，程序校验、人工抽检。用户已确认有文本 API，资料提供后接入；原文不得被改写为模型引语。
5. **失败和费用**：建议每轮最多 10 查询/20 正文、10 分钟；HTTP 每页 20 秒、2 MB、同域串行。拒绝访问不重试，429/临时错误最多重试一次且计入上限；没正文仍输出 partial。开始前预留额度，完成后记实际消耗，实际费用未知可为空。
6. **最低抓取边界**：只收 HTTP(S)，拒绝本机/内网，检查 DNS 和每次重定向；重定向到分类页不能算详情成功。固定来源域名，网页指令当文本。
7. **输出验收**：新搜索得到不同于本轮快照的真实结果；每项能打开来源、区分摘要/原文/推测；失败、重复与费用能追溯；同批结果重复处理不重复计数。

这条链路只证明 R02/R03/R09 的单人研究闭环。邀请小分队前再补 R01、R04—R08：账户隔离、服务器持久任务、保存跟进与额度，不承诺当前已是多人 MVP。
