## 学习目标

- 把“能连上”升级成“可上线”
- 学会先用 3 个验证请求验收接入层
- 看懂常见鉴权、路径、限速和超时问题的排查顺序
- 配出主路由、受控回退和直连基线，并知道哪些错误不该自动重试

## 适合谁

- 已经接成功过一次，但不太敢长期依赖的人
- 连接之后经常遇到模型名错误、限速或超时的人
- 准备把接入层交给工具长期调用的人

## 前置条件

- 已经理解接入层的四层结构
- 已经分清 Base URL、API Key、模型名三件事

## 核心知识

### 1. 先做 3 个验证，不要直接上真实主流程

最稳的顺序通常是：

1. **最小请求**  
   验证地址、Key、模型名能不能走通

2. **长上下文请求**  
   验证上游、代理层和工具之间对大输入的处理是否稳定

3. **真实任务请求**  
   验证输出格式、耗时和你真正依赖的能力是否正常

如果只做第 1 步就宣布“接通了”，你很快会在真实任务里补课。

### 2. 最小验证必须先确认接口类型

“OpenAI 兼容”不是一个单一端点。下游工具可能依赖 Chat Completions，也可能依赖 Responses API 或供应商原生接口。先看工具和服务方的官方文档，确认它实际要求的路径、请求体与鉴权方式。

只有当文档明确支持 Chat Completions 兼容接口时，最小请求才可以类似这样：

```bash
curl "$BASE_URL/chat/completions" \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "your-default-model",
    "messages": [
      { "role": "user", "content": "reply with ok" }
    ]
  }'
```

注意：有的平台要求 `BASE_URL` 填到 `/v1`，有的平台要求只填域名再由工具补路径；还有些工具会直接调用 Responses API。不要把一段 `curl` 当成通用答案，必须以当前官方接入说明为准。

你要看的不是只有 `200`，还包括：

- 延迟是不是异常长
- 返回模型名是不是你预期那一个
- 错误信息是不是足够明确

### 3. 常见报错怎么查，哪些情况不要盲目重试

| 报错 | 最常见原因 | 第一检查点 |
| --- | --- | --- |
| 401 / 403 | Key 无效、项目或工作区权限不足、调用方无权访问目标能力 | 凭据归属、项目权限和上游鉴权；修正前不要重试 |
| 404 | 路径不受支持、API 版本不匹配、资源或模型名不可用 | 官方端点说明、Base URL 和模型映射 |
| 429 | 请求速率、令牌速率、并发或用量限制被触发 | 响应头、官方限额页和网关限流；按文档做退避 |
| 5xx | 上游或代理层暂时异常 | 服务状态、网关日志和回退条件；只做有上限的重试 |
| timeout | 网络、上游、代理或请求规模导致超时 | 分层记录耗时，缩小请求后定位，不要无限重试 |
| 模型不存在 | 官方模型名变更、网关别名未映射、白名单未开放 | 模型列表、别名映射和访问权限 |

对 429、5xx 和部分网络错误，可以按服务方建议使用带抖动的指数退避并设置最大次数；鉴权、参数、路径和权限错误应先修配置。涉及写入、发信、支付等副作用时，还要先确认请求是否可安全重放。

### 4. 回退要分三层

真正可用的接入层，建议至少准备三类路线：

| 层级 | 作用 |
| --- | --- |
| 主路由 | 通过真实任务验收的默认模型与供应方 |
| 受控回退 | 只对明确的暂时性错误切换到已验收的备用路由 |
| 直连基线 | 代理层异常或需要核验供应商原生能力时使用 |

举个例子：

- 主路由：日常高频、成本和质量都通过验收的路线
- 受控回退：能力、数据区域、内容政策和成本差异已经写清的备用路线
- 直连基线：把核心任务切回供应商原生接口，用于恢复服务或确认兼容层差异

回退最大的意义不是“永远不出问题”，而是：

> 出问题时，不需要现场重新发明流程。

### 5. 工具接入前的检查表

在把接入层交给 Codex、Claude Code、OpenClaw 之前，先确认：

- Base URL 是否是最终稳定地址
- 凭据是否按平台能力使用独立项目、工作区、服务账号或网关虚拟 Key 隔离
- 模型名是否是这个工具真正能用的别名
- 工具实际调用的是 Chat Completions、Responses API 还是供应商原生接口
- 是否已知该工具依赖哪些格式特性
- 超时和限速时是否有带上限的重试、回退或人工接管路径

只有这些确认过，才适合让工具长期调用。

### 6. OpenAI 兼容要按能力验收

“兼容”不等于“所有能力一致”。至少按下面几项测：

| 能力 | 最小验收方法 | 不通过时怎么办 |
| --- | --- | --- |
| 普通对话 | 最小请求返回 `ok` | 查 Base URL、Key、模型名 |
| 流式输出 | 打开 stream，确认增量格式稳定 | 关闭 stream 或换原生 API |
| 工具调用 | 用一个简单函数调用测试参数结构 | 改工具配置或改用官方原生接口 |
| 长上下文 | 放入较长输入，检查是否截断或超时 | 切片处理，调整超时和模型 |
| JSON / Markdown 格式 | 用一组代表性样本检查格式稳定性 | 使用原生结构化输出、调整约束或换路线 |
| 错误码 | 故意用错 Key 或模型名 | 确认错误信息能帮助排查 |

如果你的工作流依赖某项能力，那这项能力必须单独验收。不要用“最小对话能通”替代真实能力测试。

- **可用**：三类请求和一次失败演练都通过，可以接入长期流程。
- **暂缓**：任何关键项没过，先不要交给长期工具调用。

## 一个最小验证流程

建议你按这个顺序实际操作一次：

1. 跑最小请求
2. 跑一段较长输入
3. 用自己的真实任务跑 1 次
4. 人工制造一次失败，测试回退
5. 记录模型名、耗时、错误信息和最终结论

如果你能完整做完这 5 步，这条链路才算真正进入“可用状态”。

## 常见误区

1. **只验证成功路径，不验证失败路径**
   真正要命的时候，往往发生在失败路径。

2. **看到 200 就以为万事大吉**
   真实任务能不能稳定返回你需要的格式，才是关键。

3. **把回退写在脑子里，不写在配置里**
   到了出问题那一刻，你只会更慌，不会更冷静。

## 验收标准

- 能跑完 3 类验证请求
- 能按鉴权、路径、限速、服务异常、超时和模型映射分类排查
- 能给自己的接入层配置主路由、受控回退和直连基线
- 知道哪些错误适合有限重试，哪些错误必须先修配置或人工确认
- 能写出一张给工具接入前的检查表
- 能按普通对话、流式输出、工具调用、长上下文和格式输出验收兼容性
