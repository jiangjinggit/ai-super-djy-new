## 学习目标

- 把“能连上”升级成“可上线”
- 学会先用 3 个验证请求验收接入层
- 看懂最常见的 5 类报错
- 配出默认模型、回退模型和官方回退三层兜底

## 适合谁

- 已经接成功过一次，但不太敢长期依赖的人
- 连接之后经常遇到模型名错误、限速或超时的人
- 准备把接入层交给工具长期调用的人

## 前置条件

- 已经理解接入层的四层结构
- 已经分清 Base URL、API Key、模型名三件事

## 核心知识

### 1. 先做 3 个验证，不要直接上真实主流程

最稳的顺序通常是：

1. **最小请求**  
   验证地址、Key、模型名能不能走通

2. **长上下文请求**  
   验证上游、代理层和工具之间对大输入的处理是否稳定

3. **真实任务请求**  
   验证输出格式、耗时和你真正依赖的能力是否正常

如果只做第 1 步就宣布“接通了”，你很快会在真实任务里补课。

### 2. 一个通用的最小验证示例

如果你的接入层是 OpenAI 兼容入口，最小请求大致长这样：

```bash
curl "$BASE_URL/chat/completions" \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "your-default-model",
    "messages": [
      { "role": "user", "content": "reply with ok" }
    ]
  }'
```

注意：有的平台要求 `BASE_URL` 填到 `/v1`，有的平台要求只填域名再由工具补路径。不要只照抄路径，先看对应平台或代理项目的官方接入说明。

你要看的不是只有 `200`，还包括：

- 延迟是不是异常长
- 返回模型名是不是你预期那一个
- 错误信息是不是足够明确

### 3. 最常见的 5 类报错怎么查

| 报错 | 最常见原因 | 第一检查点 |
| --- | --- | --- |
| 401 | Key 不对、过期、权限不足 | 管理层 Key 和上游鉴权 |
| 404 | Base URL 路径错、模型名不存在 | 地址路径和模型映射 |
| 429 | 限速、额度打满、并发过高 | 上游配额和管理层限流 |
| timeout | 上游慢、代理复用差、请求太重 | 代理层和上游状态 |
| 模型不存在 | 别名未映射、模型白名单未开放 | 模型名和路由规则 |

很多“神秘问题”都不是神秘问题，只是你还没把排查顺序标准化。

### 4. 回退要分三层

真正可用的接入层，建议至少准备三层兜底：

| 层级 | 作用 |
| --- | --- |
| 默认模型 | 平时 80% 请求走的主力模型 |
| 回退模型 | 默认模型失败时临时切换 |
| 官方回退 | 整个代理层异常时的最后兜底 |

举个例子：

- 默认模型：日常高频的主力
- 回退模型：同类能力、稍贵或稍慢但更稳的备选
- 官方回退：把核心任务切回官方直连，先保住可用性

回退最大的意义不是“永远不出问题”，而是：

> 出问题时，不需要现场重新发明流程。

### 5. 工具接入前的检查表

在把接入层交给 Codex、Claude Code、OpenClaw 之前，先确认：

- Base URL 是否是最终稳定地址
- API Key 是否是该工具专用的 Key
- 模型名是否是这个工具真正能用的别名
- 是否已知该工具依赖哪些格式特性
- 超时和限速时是否有替代路径

只有这些确认过，才适合让工具长期调用。

### 6. OpenAI 兼容要按能力验收

“兼容”不等于“所有能力一致”。至少按下面几项测：

| 能力 | 最小验收方法 | 不通过时怎么办 |
| --- | --- | --- |
| 普通对话 | 最小请求返回 `ok` | 查 Base URL、Key、模型名 |
| 流式输出 | 打开 stream，确认增量格式稳定 | 关闭 stream 或换原生 API |
| 工具调用 | 用一个简单函数调用测试参数结构 | 改工具配置或改用官方原生接口 |
| 长上下文 | 放入较长输入，检查是否截断或超时 | 切片处理，调整超时和模型 |
| JSON / Markdown 格式 | 用真实输出格式测试 2 次 | 加强提示词或换模型 |
| 错误码 | 故意用错 Key 或模型名 | 确认错误信息能帮助排查 |

如果你的工作流依赖某项能力，那这项能力必须单独验收。不要用“最小对话能通”替代真实能力测试。

## 配置验收表

把每个工具接入前的结果写下来：

| 工具 | Base URL | Key 类型 | 模型名/别名 | 最小请求 | 长上下文 | 真实任务 | 失败演练 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Codex | （填） | test | （填） | 通过/失败 | 通过/失败 | 通过/失败 | 通过/失败 | 可用/暂缓 |
| Claude Code | （填） | test | （填） | 通过/失败 | 通过/失败 | 通过/失败 | 通过/失败 | 可用/暂缓 |
| OpenClaw | （填） | test | （填） | 通过/失败 | 通过/失败 | 通过/失败 | 通过/失败 | 可用/暂缓 |

结论只有两类：

- **可用**：三类请求和一次失败演练都通过，可以接入长期流程。
- **暂缓**：任何关键项没过，先不要交给长期工具调用。

## 一个最小验证流程

建议你按这个顺序实际操作一次：

1. 跑最小请求
2. 跑一段较长输入
3. 用自己的真实任务跑 1 次
4. 人工制造一次失败，测试回退
5. 记录模型名、耗时、错误信息和最终结论

如果你能完整做完这 5 步，这条链路才算真正进入“可用状态”。

## 常见误区

1. **只验证成功路径，不验证失败路径**
   真正要命的时候，往往发生在失败路径。

2. **看到 200 就以为万事大吉**
   真实任务能不能稳定返回你需要的格式，才是关键。

3. **把回退写在脑子里，不写在配置里**
   到了出问题那一刻，你只会更慌，不会更冷静。

## 验收标准

- 能跑完 3 类验证请求
- 能看懂 401 / 404 / 429 / timeout / 模型不存在 这 5 类常见报错
- 能给自己的接入层配置三层回退思路
- 能写出一张给工具接入前的检查表
- 能按普通对话、流式输出、工具调用、长上下文和格式输出验收兼容性
