## 学习目标

- 分清官方直连、自建接入层、第三方中转三条路线
- 学会按任务敏感度和团队约束做选择
- 知道哪些任务默认必须保留官方直连
- 带走一张 5 分钟判断表

## 适合谁

- 正在纠结“要不要自己搭”的人
- 想把现在混乱的接入方案梳理成默认路线的人
- 已经在用第三方中转，但不知道边界该怎么设的人

## 前置条件

- 知道 API 中转大概是什么
- 已经用过至少一种 API 或 AI 工具

## 核心知识

### 1. 三条路线先分开看

很多讨论把所有“中转”混在一起，导致后面越聊越乱。

先拆成三条路线：

| 路线 | 定义 | 最大优点 | 最大代价 |
| --- | --- | --- | --- |
| 官方直连 | 工具直接访问官方模型服务 | 最确定、最清楚、最少中间层 | 支付、配置和多工具复用更分散 |
| 自建接入层 | 你自己控制代理层或管理层 | 可统一入口、可做回退、可做治理 | 你自己要承担最小运维成本 |
| 第三方中转 | 别人搭好，你只拿地址和 Key 用 | 上手快、前期最省事 | 信任、掺水、日志、跑路风险都更高 |

这三条路线没有绝对优劣，只有适不适合当前任务。

### 2. 先按任务分层，而不是按人分层

选择接入方式时，最容易犯的错是直接问：

> “我是个人用户，所以我该用哪种？”

更好的问题是：

> “我这类任务，需要哪种链路？”

一个人也可能同时拥有三种链路：

- 高敏感任务：官方直连
- 日常实验与公开资料整理：自建接入层
- 临时试用或低风险体验：第三方中转

所以真正的分法不是“个人 vs 团队”，而是“任务风险层级”。

### 3. 默认保留官方直连的任务

下面这些任务，我建议默认保留官方直连或完全自控链路：

- 私有代码仓库的高敏感部分
- 客户资料、合同、内部经营数据
- 支付、发信、数据库写入
- 包含 secrets、生产配置或可执行高权限动作的上下文
- 需要高度依赖官方特性的能力验证

因为这些任务一旦出问题，损失不是“模型答偏一点”，而是数据、权限或业务层面的损失。

### 4. 自建接入层最适合什么

自建接入层最适合这几类情况：

- 你要把多个工具统一接到同一入口
- 你已经开始用多个模型或多个账号体系
- 你希望做回退、限速、配额和模型白名单
- 你需要给自己或小团队建立一套可复用默认配置

换句话说：

> 自建不是为了显得技术强，而是为了把“接模型”从一次性配置，变成长期可复用的基础设施。

### 5. 第三方中转到底什么时候还可以用

不是说第三方一律不能用，而是默认信任等级要更低。

相对可接受的场景：

- 你在做低风险实验
- 输入内容本身就是公开资料
- 你只是临时体验某个工具能不能跑通
- 你明确接受“质量、日志和稳定性不可完全控”的事实

不适合的场景：

- 想把它当长期主链路
- 拿它跑高敏感 Prompt
- 价格便宜得反常，但你又无法验证模型真实性

## 5 分钟判断表

给每个任务打一遍：

| 问题 | 如果答案是“是” | 默认倾向 |
| --- | --- | --- |
| 这个任务是否包含敏感数据？ | 是 | 官方直连 |
| 是否需要多个工具共享同一入口？ | 是 | 自建接入层 |
| 是否需要回退和配额治理？ | 是 | 自建接入层 |
| 是否只是临时测试与公开资料处理？ | 是 | 第三方中转可考虑 |
| 是否必须保证模型真实性和特性一致？ | 是 | 官方直连优先 |

## 练习：给 3 个真实任务做链路分流

不要只在脑子里判断。把你的任务填进这张表：

| 任务 | 数据敏感度 | 是否多人共享 | 是否需要回退/配额 | 默认链路 | 为什么 | 失败时怎么退 |
| --- | --- | --- | --- | --- | --- | --- |
| 读取私有仓库做重构建议 | 高 | 否 | 需要 | 官方直连或完全自控 | 减少不必要中间层 | 切回官方直连和人工审查 |
| 整理公开 AI 新闻 | 低 | 是 | 需要 | 自建接入层 | 统一多个工具和模型 | 切回官方直连或备用模型 |
| 临时测试陌生插件 | 低 | 否 | 不需要 | 第三方中转可考虑 | 只看能否跑通 | 不进入长期流程 |

### 分流表要写清 3 条边界

1. **数据边界**：哪些输入不能经过第三方代理。
2. **能力边界**：哪些任务必须保证官方特性、模型真实性或工具调用行为。
3. **回退边界**：代理不可用时，是切模型、切网关，还是回到官方直连。

如果一项任务说不清这 3 条边界，默认不要走第三方中转。

## Demo

### 任务 1：让 Codex 读取私有仓库并生成重构建议

默认路线：**官方直连**

原因：

- 仓库本身敏感
- 上下文可能包含 secrets 或业务逻辑
- 需要尽量减少不必要的中间链路

### 任务 2：用 OpenClaw 每天整理公开 AI 新闻

默认路线：**自建接入层**

原因：

- 数据是公开的
- 可能同时接多个模型与多个工具
- 更适合做统一入口、限速和回退

### 任务 3：临时试一个陌生工具能不能跑通

默认路线：**第三方中转可接受**

前提：

- 只处理低风险公开内容
- 只是短期试用
- 心里清楚这不是你要长期依赖的主链路

## 常见误区

1. **觉得“既然能中转，那就都中转”**
   这会把最不该冒险的任务也送进代理层。

2. **只用“个人 / 团队”做判断**
   任务风险和链路要求，比身份标签更重要。

3. **把第三方中转当成长期主方案**
   你迟早会为日志、质量或稳定性付出额外成本。

## 验收标准

- 能说清三条路线分别是什么
- 能列出至少 4 类默认保留官方直连的任务
- 能按任务而不是按身份做链路选择
- 能用一张判断表给自己的 3 个真实任务分流
- 能为每个任务写出失败时的回退路线
