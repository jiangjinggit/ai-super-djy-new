## 学习目标

- 看懂一条 API 请求经过哪些层
- 分清 Base URL、凭据、API 类型和模型名
- 理解“OpenAI 兼容”为什么仍需验证

## 1. 请求链路只有四层

```text
模型供应商 / 云平台
    ↓
网关（转发、路由、模型映射）
    ↓
管理层（凭据、预算、权限、必要日志）
    ↓
下游工具或脚本
```

有些产品把网关和管理层做在一起，但排查时仍要分开理解：到底是上游异常、路由错误、权限不足，还是下游配置不对。

## 2. 四项配置不要混

| 配置 | 回答的问题 | 常见错误 |
| --- | --- | --- |
| Base URL | 请求发到哪里？ | 路径多写或少写 `/v1` |
| 凭据 | 谁在调用，有什么权限和预算？ | 测试和正式环境共用同一权限 |
| API 类型 | 使用哪个接口协议？ | 把 Chat Completions 当成唯一标准 |
| 模型名 | 调用哪个模型或网关别名？ | 别名映射到错误上游 |

平台支持时，优先用独立项目、工作区、服务账号或网关虚拟 Key 隔离测试、正式和不同调用方。

## 3. “OpenAI 兼容”只说明部分接口可适配

兼容范围可能只覆盖 Chat Completions，也可能还支持 Responses、Embeddings 或其他端点。它不自动保证以下能力一致：

- 工具调用和结构化输出
- 多模态与流式响应
- 系统指令处理
- 错误码、限额和超时行为
- 供应商原生扩展能力

因此先确认下游工具实际调用什么接口，再查看服务方官方文档。

## 本课练习

画出自己的四层链路，并填完至少一行配置表。

完成标准：别人只看这张图和表，就能知道请求发到哪里、用什么接口、由谁授权，以及出现问题先查哪一层。
