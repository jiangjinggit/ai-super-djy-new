## 学习目标

- 用一张图理解上游、代理层、管理层、下游工具的关系
- 搞清 `Base URL`、`API Key`、`模型名` 三件套分别管什么
- 理解“OpenAI 兼容”为什么不等于“完全兼容”
- 能画出自己的最小接入架构

## 适合谁

- 总是把地址、密钥、模型名混在一起的人
- 已经能接 API，但遇到报错时说不清该查哪一层的人
- 准备把接入方案从单点配置升级成系统的人

## 前置条件

- 知道直连和中转的区别
- 至少改过一次工具里的 API 配置

## 核心知识

### 1. 先画四层结构

一个完整的模型接入系统，通常可以拆成四层：

```text
上游账号 / 模型提供方
    ↓
代理层（转发、路由、模型映射）
    ↓
管理层（Key、配额、日志、白名单、监控）
    ↓
下游工具（Codex / Claude Code / OpenClaw / 自己的脚本）
```

不要把这四层混成一个概念。

- **上游** 决定你真正能调用什么能力
- **代理层** 决定请求怎么被转发和改写
- **管理层** 决定谁能用、怎么限额、怎么记账
- **下游工具** 只是请求发起者

### 2. Base URL、API Key、模型名分别是什么

这是整个模块里最值得彻底理顺的三件事。

| 概念 | 它回答的问题 | 常见误解 |
| --- | --- | --- |
| Base URL | 我请求发到哪一层服务？ | 以为它等于模型名 |
| API Key | 我是谁、我有没有权限和额度？ | 以为换 Key 就等于换模型 |
| 模型名 | 这次请求想要哪个能力？ | 以为模型名永远和官方完全一致 |

举个最简单的例子：

- Base URL 可能是你自己的网关地址
- Key 可能是你在管理层里发给自己的 test Key
- 模型名可能是一个你自己定义的别名，背后再映射到真正上游模型

所以很多看起来“模型不对”的问题，根本不是模型本身的问题，而是地址、身份和映射混了。

### 3. OpenAI 兼容只是一种“接口形状”

很多代理层或平台会说自己“兼容 OpenAI”。  
这句话通常只说明一件事：

> 你的请求格式大致能发过去。

它**不**保证下面这些都完全一样：

- 模型名命名规则
- 工具调用和函数调用行为
- 流式输出格式
- 系统提示词处理方式
- 多模态能力
- 错误码与限速策略

所以“兼容”更像是一个起点，不是终点。

一些模型平台会提供 OpenAI 兼容接口，但官方文档通常也会说明：这类接口主要服务于迁移或复用 OpenAI SDK，不代表所有原生能力、参数、工具调用和长期生产约束都完全等价。长期主链路仍建议对照各家的原生 API 文档验收，具体兼容范围以官方当前说明为准。

你真正要验证的是：

1. 这个工具能不能发请求
2. 这个模型名是不是被正确路由
3. 这个任务类型能不能稳定返回你需要的格式

### 4. 配置清单要把三件套写在一起

不要把配置散落在聊天记录、截图和工具面板里。至少维护一份这样的清单：

| 配置项 | 示例写法 | 验收方式 |
| --- | --- | --- |
| 下游工具 | Codex / Claude Code / OpenClaw / 脚本 | 确认这个工具实际读取哪份配置 |
| Base URL | 官方地址或你的网关地址 | 用最小请求确认路径是否正确 |
| Key 类型 | test / daily / team / prod | 确认权限、额度和所属成员 |
| 模型名 | 官方模型名或网关别名 | 确认映射到预期上游 |
| 默认路由 | 默认模型和供应方 | 用真实任务核验返回质量 |
| 回退路由 | 回退模型或官方直连 | 人工制造失败并演练切换 |
| 日志策略 | 关闭 / 脱敏 / 仅统计 | 确认是否会保留 Prompt 和上下文 |

这张清单的价值不是“好看”，而是出问题时你知道先查哪一层。

### 5. 最小可用架构 vs 多人架构

#### 最小可用架构

适合单人自用：

```text
上游模型
  ↓
一个代理入口
  ↓
Codex / Claude Code / OpenClaw
```

只要你能验证地址、Key、模型名和回退，这就已经够用了。

#### 多人共享架构

适合 3-10 人使用：

```text
上游模型 / 账号池
  ↓
代理层
  ↓
管理层（成员 Key / 配额 / 日志 / 模型白名单）
  ↓
多个工具和多个使用者
```

一旦进入多人共享阶段，管理层就不再是“锦上添花”，而是必须存在的控制面。

## 你自己的架构图该怎么画

先拿一张纸，按下面顺序写：

1. 上游有哪些来源
2. 中间有没有代理层
3. 谁在负责发 Key、控配额、做日志
4. 哪些工具会调用它
5. 哪一层出问题时由谁排查

只要你画完这五行，后面 80% 的混乱会立刻减少。

## 练习：画图后再写配置

按下面顺序做一次：

1. 画出四层结构：上游、代理层、管理层、下游工具
2. 给每个下游工具填一行配置清单
3. 标出模型名是官方名称还是网关别名
4. 标出哪个 Key 是测试用，哪个 Key 是日常用
5. 写出代理层异常时如何回到官方直连

✅ 完成标准：别人看你的图和清单，不需要问你就能知道请求会走哪条链路。

## Demo

### 单人自用的最小例子

你有：

- 一个主要模型来源
- 一个代理入口
- Codex 和 OpenClaw 两个工具

那你的图应该长这样：

```text
上游模型
  ↓
gateway.example.com
  ↓
Codex
OpenClaw
```

重点不是画得好看，而是你能说清：

- 请求先到哪
- 用哪个 Key
- 默认模型是谁
- 失败后切去哪

## 常见误区

1. **把代理层和管理层当成同一个东西**
   代理负责转发，管理负责控制。很多项目会同时做两件事，但逻辑上它们不是同一层。

2. **以为 Base URL 一改，其他都自动成立**
   如果模型名映射没对上，或者 Key 权限不对，照样会错。

3. **以为“兼容 OpenAI”就能无脑替换**
   真实任务格式、工具调用和报错处理，往往还要单独验证。
