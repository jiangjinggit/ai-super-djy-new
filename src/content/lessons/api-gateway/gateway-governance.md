## 学习目标

- 理解中转站本质上也是一层信任系统
- 知道 Prompt、上下文、工具输出为什么都算敏感数据
- 能识别掺水、异常低价和跑路风险
- 建立一套最小治理规则

## 适合谁

- 已经在用第三方中转，想补齐风险判断的人
- 准备把接入层交给团队或长期工作流使用的人
- 想把“能用”升级成“可长期用”的人

## 前置条件

- 已经知道中转层会经过哪些数据
- 已经理解官方直连、自建接入层、第三方中转的区别

## 核心知识

### 1. 所有请求都会经过它，这就是治理起点

中转站本质上是代理。

这意味着：

- 你的 Prompt 会经过它
- 你的上下文会经过它
- 你的工具调用参数会经过它
- 你的函数调用输出也可能经过它

所以不要把它看成一个“透明管道”。  
从架构上说，它天然就是一个可以记录、转发、替换、限速的控制点。

### 2. “掺水”为什么难第一眼发现

所谓“掺水”，常见不是完全不能用，而是：

- 宣传一个模型，实际路由到另一个更便宜的模型
- 关键任务时切成低成本模型
- 长上下文和复杂任务时质量明显不对，但表面还能回答

它难识别的原因在于：

1. 短请求和简单问题未必能看出来
2. 用户往往没有基线对照
3. 很多人只看“能不能出字”，不看质量和一致性

所以治理里必须有“真实性验证”这一层，而不是只看价格和延迟。

### 3. 便宜本身不是问题，解释不清才是问题

低价不一定有问题，但下面这些信号要提高警惕：

- 价格低得离谱，却没有清楚的来源解释
- 只给地址和 Key，没有文档、版本说明和错误说明
- 出错时只让你“多试几次”
- 没有任何关于日志、隐私和保留策略的说明
- 没有明确的回退和服务中断处理方式

一句话：

> 真正危险的不是便宜，而是你根本不知道它为什么便宜。

### 4. 最小治理规则该怎么写

先别追求大而全。最小治理规则通常只需要这 5 条：

1. 高敏感任务默认只走官方直连或完全自控链路
2. 测试 Key、日常 Key、团队 Key 分开
3. 请求日志默认关闭，或至少先脱敏
4. 默认模型、回退模型、官方回退写成规则
5. 每周抽查一次质量、成本和异常请求

只要这五条真的落地，接入层的稳定性就会上一个台阶。

### 5. 模型真实性要有基线对照

如果你担心模型被错配或掺水，不要只问“它是不是某某模型”。更有效的是保留一组基线样本：

| 样本类型 | 用来检查什么 | 怎么做 |
| --- | --- | --- |
| 最小对话 | 是否能正常路由 | 官方直连和网关各跑一次 |
| 固定格式输出 | 格式稳定性是否一致 | 要求同一 Markdown 或 JSON 结构 |
| 长上下文摘要 | 长输入是否被截断或偷换 | 放入带编号的材料，抽查引用 |
| 工具调用样本 | function call 参数是否一致 | 用简单工具调用对照参数结构 |
| 高价值任务样本 | 质量是否明显偏离基线 | 用人工评分表记录差异 |

真实性验证不是一次性动作。每次换上游、换模型映射、换第三方服务或升级网关配置，都要抽样复测。

### 6. 日志策略要先写“不要记录什么”

很多人写日志策略，只写“记录请求”。更安全的写法是先写不记录什么：

- 不记录完整 Prompt，除非明确需要调试且已经脱敏
- 不记录 secrets、客户资料、合同原文和生产配置
- 不把工具调用参数长期裸存
- 不让所有成员都能看完整日志
- 不把日志保留时间无限延长

个人网关可以只留统计：时间、模型别名、任务类型、耗时、错误码、成本区间。团队网关再根据需要补审计，但仍然要最小化。

### 7. 这不是纯技术问题，而是运营问题

很多人把 API 中转理解成“我会部署就行”。  
这只说对了一半。

真正决定它能不能长期活下去的，还包括：

- 文档是否清楚
- 回退是否及时
- 日志是否克制
- 出错时能不能定位
- 使用者是否知道边界

所以中转层一旦开始多人共享，它就不再只是技术组件，而是一套带支持成本的服务。

## 选择第三方时的 5 个检查点

如果你确实要试第三方中转，先检查：

1. 是否有清楚的文档或说明页
2. 是否说得清日志和隐私策略
3. 是否能解释模型来源和路线
4. 是否有清楚的错误提示与支持方式
5. 是否有你可以接受的回退方案

这五项里，前两项比“便不便宜”更重要。

## 团队共享前的治理表

如果准备给团队使用，至少填完这张表：

| 治理项 | 我的规则 |
| --- | --- |
| 哪些任务必须官方直连或完全自控 | |
| 哪些任务允许走网关 | |
| 哪些任务禁止第三方代理 | |
| 成员如何申请独立 Key | |
| 每个 Key 的额度和模型白名单 | |
| 日志记录什么、不记录什么、保留多久 | |
| 谁能看日志和账单 | |
| 默认模型、回退模型、官方回退分别是什么 | |
| 发现模型错配或质量异常时怎么暂停 | |
| 每周或每月谁负责复盘 | |

这张表写不清，就不要把网关当团队基础设施。

## Demo

### 场景：给团队接入一个陌生第三方网关

如果你只问两个问题：

- 便宜吗？
- 能用吗？

那后面最容易出事。

你至少还要补问：

- 日志留多久？
- 出问题怎么回退？
- 模型路由是否可验证？
- 哪些任务禁止过这层？

这些问题才决定它是不是能进你的长期流程。

## 常见误区

1. **把治理理解成“上线后再补”**
   接入层的治理越往后补，代价越高。

2. **把隐私风险理解成“也许会发生”**
   从架构上说，请求就是会经过它。区别只在于它会不会存、会不会看、会不会替换。

3. **以为只要自己搭，就自动安全**
   自建能减少外部不确定性，但如果你自己不写边界、不做回退、不控日志，同样会翻车。

## 验收标准

- 能解释为什么中转层天然是一层信任系统
- 能说出掺水和异常低价最该警惕的地方
- 能写出 5 条最小治理规则
- 能给第三方中转列出一张 5 项检查表
- 能用基线样本验证模型真实性和兼容性变化
- 能写出团队共享前的日志、白名单和敏感任务边界
