## 学习目标

- 分清单人自用和多人共享的接入目标完全不同
- 知道什么时候只做最小自用版就够了
- 理解多人版为什么必须引入管理层
- 学会从“能用”升级到“可管”的最小步骤

## 适合谁

- 想自己搭一套，但又怕复杂度过高的人
- 已经开始把地址和 Key 发给别人，但还没治理规则的人
- 准备给小团队统一 AI 工具入口的人

## 前置条件

- 已经知道接入层的四层结构
- 能看懂最基本的工具配置

## 核心知识

### 1. 自用版的目标不是“功能全”，而是“稳”

单人自用最容易走偏的地方，是一上来就追求：

- 完整面板
- 多角色系统
- 精细计费
- 花哨路由

结果通常是：搭得很复杂，但真正日常还是只用一两条链路。

单人自用最小目标其实只有四件事：

1. 有统一入口
2. 有测试 Key 和日常 Key
3. 有一个默认模型和一个回退模型
4. 故障时能切回官方直连

先把这四件事做好，比一开始上“全功能平台”更重要。

### 2. 多人共享的难点不在部署，而在规则

很多人以为，多人版只是“自用版放大”。  
其实从一个人到多人，难点变的不是命令，而是下面这些问题：

- 谁可以用哪些模型
- 谁的额度在烧
- 谁能看日志
- 谁能跑高风险任务
- 某个用户把请求打满了以后怎么办

这些都不是代理层自动帮你解决的，它们需要管理层和规则层。

### 3. 多人版最少要补哪些能力

如果开始共享给 3-10 人用，我建议至少补齐下面这些控制面：

| 能力 | 作用 |
| --- | --- |
| 成员 Key 分离 | 能知道是谁在用、谁出的问题 |
| 配额或限速 | 避免一个人把整条链路打爆 |
| 模型白名单 | 不让所有人默认访问所有模型 |
| 请求日志或统计 | 至少知道失败率、耗时和大概流量 |
| 回退规则 | 某个模型挂了以后，统一切到哪 |

没有这些控制面，就算短期也能“跑起来”，后面定位问题会越来越痛苦。

### 4. 什么时候别急着做多人版

如果你符合下面三条里的两条，先别扩到多人：

- 你自己还没稳定跑满 7 天
- 你还没有写清敏感任务边界
- 你还没演练过一次回退

很多所谓“共享网关”的第一波崩溃，不是技术原因，而是根本没有完成单人阶段的收口。

## 一个实用的演进顺序

建议按这个顺序升级：

### 阶段 1：单人最小版

- 一个入口
- 两套 Key
- 默认模型 + 回退模型
- 官方回退地址

### 阶段 2：单人稳定版

- 补充验证记录
- 开始看耗时和限速
- 把常用工具都接到同一入口

### 阶段 3：小团队版

- 成员独立 Key
- 配额和模型白名单
- 基本日志和异常定位

### 阶段 4：共享服务版

- 更细的角色权限
- 更正式的审计和支持流程
- 更清楚的 SLA 和支持成本

你会发现，真正难的不是从 0 到 1，而是从 1 到“别人也能安心用”。

## 升级前的验收闸门

每升一级之前，先问自己有没有交付物：

| 当前阶段 | 可以升级的条件 | 暂停升级的信号 |
| --- | --- | --- |
| 个人直连 | 官方 Key、模型名、账单和最小请求都跑通 | 官方直连都不稳定，还想先加代理层 |
| 单人最小版 | test/daily Key 分开，默认模型和官方回退已验证 | 只验证了 200，没有跑真实任务 |
| 单人稳定版 | 3 类验证请求和一次失败演练都完成 | 真实任务格式不稳，回退只写在脑子里 |
| 小团队版 | 成员 Key、配额、白名单、日志和敏感边界写清 | 还在多人共用同一个 Key |

把它理解成“闸门”会更稳：没有交付物，就不要把复杂度往上推。

## 练习：写出你的升级说明

如果你准备从单人自用升级到团队共享，先写一页说明：

```text
当前阶段：
准备升级到：

为什么需要升级：

允许使用的人：
允许使用的任务：
禁止使用的任务：

每个人如何拿到独立 Key：
每个 Key 的额度和模型白名单：
日志记录什么，不记录什么：

默认模型：
回退模型：
官方回退路径：

谁负责排查故障：
什么时候暂停共享入口：
```

如果这页说明写不完整，先不要共享给别人用。

## Demo

### 方案 A：你自己重度用 Codex 和 OpenClaw

建议：**只做单人最小版**

理由：

- 重点是统一入口和回退
- 不必一开始就加成员系统
- 先把验证和切换流程练熟

### 方案 B：你和 4 个同事共用一套入口

建议：**至少进入小团队版**

必须补的东西：

- 每个人独立 Key
- 模型白名单
- 额度与错误统计
- 回退说明

否则你很快就会遇到这种场景：

> “今天到底是谁把请求打爆了？”  
> “为什么这个同事能用到不该开放的模型？”  
> “日志里这个报错是哪条工具链打出来的？”

## 常见误区

1. **把多人版理解成更大的代理层**
   多人版真正增加的是治理难度，不是流量大小本身。

2. **自己还没跑稳，就开始发给别人**
   这是最经典的“把未验证系统外包给同事做测试”。

3. **共享入口但不分 Key**
   一旦出问题，你几乎无法定位责任和链路。

## 验收标准

- 能说清自用版和多人版的核心目标差异
- 知道多人共享最少要补哪 5 类控制能力
- 能判断自己当前阶段更适合停留在哪一层
- 能写出从单人到小团队的升级顺序
- 能用升级闸门判断什么时候该暂停扩张
