## 学习目标

- 判断自己是否真的需要 API 网关
- 分清官方直连、自建网关和第三方中转
- 给真实任务选一条默认链路

## 1. API 网关到底是什么

它位于模型服务和下游工具之间，常见作用只有几项：

- 统一多个工具的接入地址
- 映射不同供应商的模型名
- 为不同调用方分配凭据和预算
- 设置限速、监控和故障回退

它不是必需品，也不等于“低价模型资源”。如果没有明确需求，增加一层只会让排查更复杂。

## 2. 三条路线怎么选

| 路线 | 更适合 | 主要代价 |
| --- | --- | --- |
| 官方直连 | 单一模型、敏感任务、原生能力验证、关键生产链路 | 多个供应商和工具要分别管理配置 |
| 自建网关 | 多个工具或调用方需要统一配置、预算、权限和回退 | 自己承担稳定性、数据和运维责任 |
| 第三方中转 | 能接受其数据与稳定性风险的低风险临时任务 | 模型来源、日志和服务持续性不完全可控 |

默认原则很简单：

> 不确定是否需要网关时，先保持官方直连。

## 3. 哪些任务不要随便经过第三方

下面这些任务应优先官方直连或完全自控：

- 私有代码、客户资料、合同和内部经营数据
- 包含密钥、生产配置或高权限工具参数的上下文
- 发信、支付、数据库写入等有实际副作用的操作
- 需要核验供应商原生特性的能力测试

关键不是“官方一定没有风险”，而是减少不必要的中间方，并按供应商的数据政策做选择。

## 4. 一张判断表

为每个任务回答四个问题：

1. 是否包含敏感数据或高风险动作？
2. 是否有多个工具或调用方需要统一管理？
3. 是否确实需要预算、权限或回退控制？
4. 新增中间层带来的收益是否大于维护成本？

如果只是单一工具、低频调用，而且没有治理需求，保持直连即可。
