# 入口地图：App、IDE、CLI、Cloud 怎么选

## 本课目标

你要建立一张 Codex 入口地图，知道什么时候用 App，什么时候用 IDE，什么时候用 CLI，什么时候把任务交给 Cloud。

## 四类入口

Codex 的入口可以粗略分成四类：

- App：适合从产品化界面发起任务、查看任务结果、管理云端协作。
- IDE：适合在编辑器里做局部修改、解释代码、补测试、跟随当前文件上下文工作。
- CLI：适合在本地仓库里读文件、跑命令、看 diff、执行明确的工程任务。
- Cloud：适合把低耦合、可描述、可验收的任务交给云端后台执行，并通过 PR 或任务结果审查。

入口没有绝对高低。关键看任务依赖和反馈节奏。

## 选择标准

先问三个问题：

1. 这个任务是否强依赖本机环境？
2. 我是否需要实时观察每一步 diff？
3. 这个任务能不能被清楚写成输入、边界和验收标准？

如果强依赖本机环境，优先 CLI 或 IDE。  
如果需要边看边改，优先 IDE。  
如果任务清晰、低耦合、可以后台跑，适合 Cloud。  
如果只是浏览任务状态或发起云端任务，可以用 App。

## 推荐起步路线

新手不要一开始就把任务丢给 Cloud。建议顺序是：

1. 用 CLI 或 IDE 做只读分析。
2. 用 CLI 或 IDE 做一次小范围改动。
3. 写好 AGENTS.md 和任务契约。
4. 把低风险、低耦合任务交给 Cloud。

这样做会慢一点，但能让你看清 Codex 是怎么读、怎么改、怎么犯错的。

## 练习

列出 8 个你最近一周真实遇到的任务，例如：

- 修一个 Bug。
- 补一段文档。
- 给组件加测试。
- 整理接口说明。
- 调整页面样式。
- 做依赖升级评估。
- 生成 PR 描述。
- 审查一段代码。

给每个任务选择入口，并写一句理由。

## 验收标准

你的表格里每个任务都包含：

- 推荐入口。
- 不推荐入口。
- 风险等级。
- 验证方式。
- 是否需要人工确认。

能做到这一点，说明你已经开始把 Codex 当成工程协作工具，而不是随手试一试的聊天框。
