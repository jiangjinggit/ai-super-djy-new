# Sandbox 与 approvals：把危险能力关进笼子

## 本课目标

理解 Codex 的两类安全控制：

- Sandbox：限制它能接触什么资源。
- Approvals：决定哪些动作要经过你确认。

这不是麻烦的提示框，而是让 AI 编程可控的底座。

## 为什么需要权限边界

Codex 能读文件、写文件、运行命令。能力越强，误操作成本越高。

常见风险包括：

- 删除或覆盖用户未提交改动。
- 安装不必要依赖。
- 修改生产配置。
- 发起外部网络请求。
- 执行危险脚本。
- 推送未经审查的代码。

不要靠“模型应该不会这么做”来管理风险。要靠权限、确认点、diff 和回退路径。

## 风险分层

低风险：

- 只读分析。
- 解释代码。
- 生成计划。

中风险：

- 修改工作区文件。
- 运行本地测试。
- 批量改文档。

高风险：

- 删除文件。
- 安装或升级依赖。
- 改环境变量和部署配置。
- 发外部请求。
- 操作数据库。
- git push 或发布。

高风险操作必须人工确认。

## 放权顺序

推荐顺序：

1. 只读。
2. 允许工作区内小范围写入。
3. 允许运行已知安全的验证命令。
4. 对稳定流程建立更顺滑的审批策略。
5. 宽权限只在隔离环境或可完全回退任务中使用。

## 练习

给你的项目写一张权限矩阵：

| 操作 | 默认策略 | 原因 | 回退方式 |
| --- | --- | --- | --- |
| 读源代码 | 允许 | 低风险 | 无需回退 |
| 修改源码 | 需计划 | 可能影响行为 | git diff / revert |
| 安装依赖 | 需确认 | 供应链风险 | 恢复锁文件 |
| 推送代码 | 禁止默认执行 | 团队审查 | 人工推送 |

## 验收标准

你能说清每个高风险操作为什么需要确认，并知道失败后怎么恢复。
