# 5 步执行法：让 Codex 按工程节奏工作

## 本课目标

把任何 Codex 任务拆成固定节奏：

1. 读。
2. 计划。
3. 执行。
4. 验证。
5. 总结。

这个流程适用于 CLI、IDE 和 Cloud。

## 第一步：读

先让 Codex 读取相关文件、测试、报错和文档。要求它输出：

- 它读了哪些文件。
- 它理解的问题是什么。
- 它认为可能原因是什么。
- 哪些地方仍然不确定。

这一阶段不要改文件。

## 第二步：计划

计划要具体到：

- 会修改哪些文件。
- 不会修改哪些文件。
- 采用什么方案。
- 运行什么验证。
- 有哪些风险。

如果计划太泛，先让它重写计划。

## 第三步：执行

确认计划后再允许修改。执行时要求：

- 严格按计划改。
- 不顺手重构。
- 不引入新依赖。
- 遇到不确定先停下。

## 第四步：验证

验证不只是“看起来没问题”。至少选择一种：

- lint。
- typecheck。
- unit test。
- build。
- 手动复现。
- 截图或页面检查。

## 第五步：总结

最后让 Codex 输出：

- 变更摘要。
- 修改文件。
- 验证结果。
- 残留风险。
- 回退方式。

## 练习

拿一个小任务，用下面模板写指令：

```text
请按 5 步执行：
1. 先读取相关文件并总结问题，不要修改。
2. 给出计划，列出会修改和不会修改的文件。
3. 我确认后再执行。
4. 修改后运行验证命令：...
5. 输出变更、验证、风险和回退方式。
禁止：...
```

## 验收标准

任务结束后，别人只看 Codex 的总结和 diff，就能判断它是否完成任务。
