# IDE 与 PR 工作流：把 Codex 接进日常开发

## 本课目标

把 Codex 放进真实研发流程，而不是让它绕过流程。

## IDE 适合什么

IDE 里的 Codex 适合即时上下文任务：

- 解释当前文件。
- 根据报错定位局部问题。
- 给函数补测试。
- 小范围重构。
- 调整组件实现。
- 生成类型或注释。

IDE 的优势是反馈快。风险是你容易连续让它改很多东西，最后 diff 失控。

## PR 工作流

AI 改动必须进入正常 PR 审查。一个好的 Codex PR 应该包含：

- 原始任务。
- 变更摘要。
- 修改文件列表。
- 验证命令和结果。
- 风险点。
- 需要人工确认的问题。

不要接受一句“已完成”。工程协作需要可审查的证据。

## 团队 checklist

建议团队统一检查：

- 是否解决原始任务。
- 是否超出修改范围。
- 是否引入新依赖。
- 是否修改配置、权限、数据库、部署相关文件。
- 是否有测试或合理验证。
- 是否包含敏感信息。
- 是否需要产品或安全人员确认。

## 练习

给你的团队写一份 Codex PR 模板：

```markdown
## 原始任务
## 改动摘要
## 验证结果
## 风险与回退
## 需要人工确认
```

## 验收标准

之后任何 Codex 生成的 PR，都能用这份模板审查，而不是凭感觉决定能不能合并。
