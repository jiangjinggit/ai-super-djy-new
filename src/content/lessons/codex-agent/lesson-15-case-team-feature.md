# 实战案例 B：产品和研发一起用 Codex 做小功能

## 场景

产品希望在学习网站里增加一个“继续学习”入口。研发担心改动影响路由、进度记录和移动端布局。

这个任务适合用 Codex，但必须先把产品验收和工程边界写清楚。

## 协作分工

产品负责：

- 用户故事。
- 页面文案。
- 交互期望。
- 验收标准。

研发负责：

- 允许修改范围。
- 不可触碰模块。
- 数据结构边界。
- 验证命令。

Codex 负责：

- 读取现有实现。
- 生成计划。
- 小范围实现。
- 补充测试或验证说明。
- 输出 PR 摘要。

## 任务契约示例

```text
目标：在首页增加“继续学习”入口，点击后进入用户最近访问的课程；如果没有记录，则进入模块列表。
范围：允许修改首页组件和已有学习进度读取逻辑；不要改路由结构和课程数据模型。
禁止：不要新增后端接口，不要引入依赖，不要改变现有模块排序。
验收：桌面和移动端布局不溢出；没有学习记录时有合理回退；运行 lint 和 build。
流程：先读现有代码并给计划，我确认后再改。
```

## Cloud 拆分

如果任务变大，可以拆给 Cloud：

1. 分析现有学习进度存储方式。
2. 实现首页入口。
3. 补充文档和手动验证清单。

每个任务都要能独立失败，不能互相覆盖。

## 与 Claude Code 的搭配

Claude Code 课程里的 CLAUDE.md 思路可以迁移成 AGENTS.md。  
5 步执行法可以迁移成 Codex task contract。  
Cowork 或文档工具整理出来的产品需求，可以转成 Codex 的仓库任务。

重点不是工具崇拜，而是把入口、权限和验收统一起来。

## 验收标准

完成一个小功能任务包：

- 产品需求。
- 技术边界。
- Codex 任务契约。
- PR checklist。
- 验收记录。

下一次类似小功能，团队能直接复用这套流程。
